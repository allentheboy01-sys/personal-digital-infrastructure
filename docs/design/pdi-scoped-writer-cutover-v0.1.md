# Scoped writer cutover operations v0.1

This is **operator-only** release tooling, not a Consumer/MCP capability. It
does not promote a deployment merely by being installed or imported. The
reviewed source release must be finalized separately, then explicitly invoked
by a human on the approved production host. No production operation is part
of development qualification.

## Preconditions and approval inputs

`scripts/mu13_p3c_cutover.py` supports `preflight`, `apply`, `verify`, and
`abort`. Each invocation requires an exact release SHA, production hostname,
approved full rollback snapshot ID, rollback source SHA, and exact pre-cutover
aggregate counts. These values are operator approval inputs, not discovery
defaults; the script never substitutes current measurements for expectations.
Release directories must be named by the full SHA under the installation's
release root. Use the release's own Python 3.13 virtual environment. All source,
dependencies, interpreter targets and parent paths must be root-controlled and
not group/world-writable. The service account must not own the release.
The administrative script prepends its release's `src` directory; the new unit
fixes `PYTHONPATH` to the current release's `src`. An older wheel left in the
virtual environment cannot silently replace the reviewed PDI source tree.

The deployment layout follows the existing scoped systemd installation:
`/opt/pdi/releases`, `/opt/pdi/current`, `/etc/pdi/scoped-staging`, and
`/etc/pdi/scoped`. These are installation contracts, not development paths.
The CLI intentionally cannot redirect production filesystem roots. Tests inject
temporary paths through Python dependency injection; this is not an operator
or model-facing privilege bypass.

Frozen staging inputs:

- `identity-plan.toml`: `[principal]` with `id`, `enabled=false`, and
  `represents="existing-personal-world"`; `[provider_instances]` maps the four
  supported Providers to frozen UUIDs; `[provider_accounts]` maps Nextcloud and
  Immich to frozen UUIDs; four `[observation_scopes.<key>]` sections contain
  `id` and `enabled=false`. Gmail preservation and integration-test quarantine
  are distinct scopes. No UUID is generated by cutover.
- `[policy]` requires Gmail ingestion disabled, zero integration-test deletion,
  legacy preservation, and `person_equals_principal=false`.
- `transition-plan.toml`: `initial_enablement` is a nonempty **string**, not a
  table. `source_mapping` must exactly match the frozen four-Provider mapping.
  `legacy_rows_mutated` and `legacy_sync_state_copy` are required historical
  fields, not commands; their contents are not invented or re-executed.
- `provider-native-ids.conf`: the two nonempty native account identity values
  must equal the corresponding existing DB Account values. They are not logged.

The root-only recovery `final-premigration.env` must match the supplied full
snapshot and source SHA, the old schema revision, PostgreSQL 16, and all three
quiescence/restore/count-equivalence success flags. Its companion human recovery
document must exist. No backup disk mounting or Restic invocation occurs.

## Exact database evidence

Before mutation, a repeatable-read **read-only** transaction verifies:

- schema `e5a7b9d1f324` and PostgreSQL 16;
- approved aggregate counts for all nine baseline tables and each Provider's
  Sources (ledger count is intentionally not a fixed historical constant);
- exactly four Instances, two Accounts, four Scopes, matching frozen UUIDs,
  relationships, native IDs, and disabled flags;
- no NULL or duplicate scoped Source identity, and exact Provider/Scope mapping;
- scoped Person/Relation observations equal their preserved legacy versions,
  including inactive state; Relation Resource/Person evidence exists;
- two initialized, non-reconciliation-required scoped states with exact initial
  legacy checkpoint/version equivalence, checked internally without output.

Subsequent checks preserve existing Source ID/Scope pairs, legacy Person,
Relation and sync-state fingerprints, preservation-Provider Source rows,
Observation/Enrichment counts, ledger identity, and nondecreasing scoped state
versions. Each qualification must add exactly its expected completed ledger row.
No ResourceRef format, World Model, or Alembic revision changes.

Evidence retained in the root-only operation journal includes Source identifiers
and opaque internal fingerprints. Do not publish or copy that journal into Git,
reports, fixtures or chat. Reports contain only fixed diagnostic codes.

## Locks and execution sequence

The independent root-only cutover control lock is held for the entire apply.
A second apply is refused immediately. The existing formal sync lock is acquired
by the script for preflight, installation, identity activation and checks, but
is **released while waiting for systemd qualification**. Each systemd child
acquires that same formal lock through the existing runner. There is no lock
bypass or manual shell file descriptor requirement.

Order:

1. Re-run all preflight checks under both locks; require legacy timers disabled,
   no legacy writer services/processes, healthy compatibility readers, tunnels
   and backup timers, no existing P3C attempt/config/schedules.
2. Durably record a `PREPARED` journal before configuration mutation, including
   the previous symlink target and baseline evidence.
3. Generate protected config, install and validate the repo-tracked service and
   generated timers, atomically replace the current-release symlink and reload
   systemd unit definitions. Existing compatibility services are not restarted.
4. In one DB transaction enable Nextcloud and Immich Instance → Account → Scope.
   Neither preservation Provider is enabled.
5. Via `pdi-p3c-writer@.service`, qualify Nextcloud incremental, Immich incremental,
   Immich Person and Immich Relation sequentially. Reacquire the formal lock
   after each service returns, verify health, invariants and ledger evidence.
6. Only after all checks pass, activate the four timers and verify enabled/active
   status. Persist `PASS`. `verify` rechecks a successful journal and live state.

## Schedule and daily chain

| Schedule | Calendar | Execution |
|---|---|---|
| Nextcloud incremental | `*:0/5` | Scope-state incremental |
| Nextcloud full | `02:15` | Authoritative scoped full |
| Immich incremental | `*:2/5` | Scope-state incremental |
| Immich daily | `05:15` | Full → Person → Relation |

The daily wrapper awaits each successful runner result. A failure or exception
prevents subsequent steps. Each step retains its existing ledger key and global
formal lock. Incremental runs may interleave between successful daily steps,
but cannot overlap a locked step. There are no guessed processing delays.
Timers use the host's existing timezone, no randomized delay, and
`Persistent=false`: no missed daily job is launched as a cutover catch-up.

## Credentials, routing and systemd

The non-secret registry is generated for the **real** `load_registries()` and
`load_scoped_operator_configuration()` contracts. It contains one approved
Principal, one DB environment reference, and exactly two Principal+Scope
Provider bindings. The DB is the existing Personal DB, resolved via
`PrincipalDatabaseRouter`; it is not copied or newly provisioned.

The script reads the existing trusted six-key environment file without shell
execution or interpolation. The supported format is literal `KEY=value` or
single/double-quoted single-line values. Ambiguous escapes, duplicate keys and
control characters fail closed rather than silently altering credentials.
Nextcloud WebDAV user-root and Immich expected-native-user checks remain in the
existing Provider adapters. There is no global credential or legacy fallback.

- Config directory: root:service-group `0750`.
- Registry: root:service-group `0640`, no DB URL or secret value.
- Unit env directory: root:root `0700`; files root:root `0600`.
- Each unit receives DB access and only its Provider's secret. PID 1 reads the
  protected EnvironmentFile before running as `pdi`; the user need not read it.
- Service: `User=pdi`, `Group=pdi`, `NoNewPrivileges=true`, protected filesystem,
  process-group stop, no secret argv. Existing template/defaults are unchanged.
- Service library stdout/stderr is not forwarded; fixed results and DB ledger
  supply operational evidence without exposing Provider exceptions/URLs.

## Abort is not database rollback

On failure, stop all new services/timers **before** waiting for the global sync
lock (a timed-out service may still hold it). Attempt every cleanup action even
if one fails. Under the sync lock, disable Scope → Account → Instance for the
two enabled Providers. Preserve the migrated schema and all P3B provenance.
Legacy writers remain disabled. Ingestion pauses.

The new release/config may remain installed but inert for diagnosis; no automatic
symlink reversal into legacy runtime occurs. The old symlink target is recorded.
Cleanup errors produce `ABORT_INCOMPLETE`, never a false assurance of safety.
Failed attempts are not silently resumed. A durable journal makes all repeated
`apply` calls refuse without mutation; explicit `abort` can be retried under
the control lock. After an abrupt kill/power failure, a human must inspect the
journal and run the reviewed abort command before any new attempt. This is not
a distributed crash-recovery coordinator.

Full DB rollback requires a separate human-authorized recovery gate using the
qualified final pre-migration snapshot. This script never invokes restore,
downgrade, backfill, checkpoint copy or legacy-writer enablement.

## Human invocation and qualification scope

After separate code review/push and immutable release staging, the human command
has this shape (placeholders are non-secret approved operational evidence):

```sh
sudo /opt/pdi/releases/<EXACT_SHA>/.venv/bin/python \
  /opt/pdi/releases/<EXACT_SHA>/scripts/mu13_p3c_cutover.py apply \
  --release /opt/pdi/releases/<EXACT_SHA> --expected-sha <EXACT_SHA> \
  --production-host <APPROVED_HOST> \
  --rollback-snapshot <FULL_APPROVED_SNAPSHOT_ID> \
  --rollback-source-sha <APPROVED_SOURCE_SHA> \
  --expected-counts '<APPROVED_TABLE_AND_PROVIDER_COUNTS>'
```

Count keys are `assets`, `blobs`, `asset_sources`, `persons`, `person_sources`,
`resource_person_relations`, `resource_statements`, `resource_enrichments`,
`provider_sync_state`, `sources.nextcloud`, `sources.immich`, `sources.gmail`,
and `sources.integration-test`. Missing keys fail closed. No credential belongs
in this command. `preflight` is informative only: `apply` always repeats it.

Development tests use temporary files, fake systemctl, synthetic SQL responses,
and actual inter-process flock handoff. They do not contact a production host
or a Provider. A real PostgreSQL integration suite requires an independently
available isolated test database and is never inferred from fake-response tests.

Scope limits remain explicit: enrichment scheduling is deferred to P3D;
Principal-bound Consumer/MCP cutover is deferred; Gmail scoped ingestion and
integration-test writers are disabled. No second Principal is onboarded.
